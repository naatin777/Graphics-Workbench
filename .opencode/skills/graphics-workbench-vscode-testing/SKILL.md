# LHG VS Codeテスト

変更された動作を確認できる最も低いテスト境界を選択する。

## visual review

UI変更では、変更した挙動に関係する状態だけを確認する。全てのUI変更で全パターンを強制しない。

確認候補:

- wide / narrow layout
- loading / empty / error / disabled state
- long filename
- many pages

Playwrightはスクリーンショットを`artifacts/visual-review/`へ生成し人間が目視確認する(pixel比較しない)。スクリーンショットだけを機能検証の代わりにしない。

## テスト境界

### Unit Test

純粋関数、パーサー、パス判定、変換オプションの組み立てに使用する。

### Integration Test

VS Code API、コマンド実行、ファイル操作、外部CLIとの接続に使用する。

### VS Code Electron / Playwright

実際のExtension Host、Webview表示、ユーザー操作、画面遷移が必要な場合に使用する。

## テスト名の粒度（処理フローの日本語訳）

テスト名は「要件名」「機能名」「結果の要約」ではなく、**そのテストコードが実際に通る処理フローを日本語に翻訳した文章**にする。テスト名を上から読むだけで、ソースコードを開かずに以下が追える状態を目指す：

- 何を入力するのか、どの状態から始まるのか
- どの関数・処理・分岐を通るのか、途中で何を判定するのか
- どの処理が実行されるのか / 実行されないのか
- 最終的に何が返る・生成される・変更されるのか
- エラー時・キャンセル時にどこで処理が止まるのか
- 一時ファイル・既存ファイルなどの副作用がどうなるのか

### 具体例

- ✗「PDFを結合する」→ ○「選択されたPDFを先頭から順番に読み込み、それぞれの全ページを同じ順番で出力PDFへ追加して、1つのPDFとして保存する」
- ✗「キャンセルを処理する」→ ○「出力先ファイルが既に存在し、上書き確認でキャンセルされた場合は変換処理を開始せず、既存の出力ファイルも変更しない」
- ✗「fallbackする」→ ○「ユーザー設定の実行ファイルパスが指定されていない場合は、OSごとの既知のインストール先を順番に確認して最初に見つかった実行ファイルを使用する」

### 規則

- 抽象語（正常 / invalid / error / fallback / cleanup / handles / works 等）だけでケースを表現しない。実際の入力・条件・結果を書く。
- 分岐条件を出す。何がtrue / falseになった結果その処理へ進むのか。重要な場合は「何をしないか」も含める。
- エラー系では失敗地点を書く（非0終了コード / ENOENT / キャンセル / 起動失敗等）。
- ファイル操作では変更前後を書く（元 / 出力 / 既存 / 一時ファイルのどれがどうなるか）。
- 数値・ページ数・角度・順序が検証内容に重要なら名前に含める（fixture上の偶然の値は不要）。
- `describe` の文脈に依存せず、`it` 単体で意味が通じる名前。CIログで個々の名前だけ見ても分かるようにする。
- **テスト名とassertionを一致させる**。検証していない挙動を推測で名前に追加しない。
- プロジェクト内部でしか意味が通じない名称（planner / job / staging / guard / envelope / record / keep-both / newer-conversion 等）は、その名称が表す実際のコードパスを日本語へ展開する。検証対象そのもの（コマンドID・設定キー・エラー文字列）と一般技術用語（smoke test / PDF / TOCTOU 等）は処理内容を併記したうえで残してよい。
- 1つのテストが複数の独立仕様を検証していて名前と検証が1対1にならない場合のみ分割する。名前が長いという理由だけで分割しない。
- テストのロジック・assertion・本番コードは変更せず、名前文字列だけを対象とする。

## 手順

1. ユーザーから観測できる期待動作を明確にする。
2. 既存テストから最も近いテスト境界を探す。
3. 実装詳細ではなく動作を検証する。
4. 実フィクスチャがある場合は再利用する。
5. 修正前に失敗を再現できることを確認する。
6. 修正後に同じテストを成功させる。

## 規則

- VS Code APIを過剰にモックしない。
- Webviewの内部実装だけを検証して完了扱いしない。
- 不安定な待ち時間の固定値を増やさない。
- PlaywrightをUnit Testで確認できる変更に乱用しない。
- スクリーンショットだけで動作確認を代用しない。
- Unit / Integration / VS Code Electron / Playwright のうち、最も低い適切な境界を選ぶ。
- 実装の検証は `graphics-workbench-verify`、Webview機能の設計は `graphics-workbench-webview-feature` を参照する。
