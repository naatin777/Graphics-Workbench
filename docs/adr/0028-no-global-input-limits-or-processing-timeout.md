# ADR-0028: アプリケーション共通の入力制限と本処理タイムアウトを設けない

## ステータス

採用

## 日付

2026-08-04

## 背景

入力ファイルサイズ制限、PDFページ数制限、処理タイムアウトを過去に何度も追加・削除してきた。制限値の技術的根拠が曖昧で、方針が安定しなかった。

- ファイルサイズは展開後のメモリ使用量を表さない（500MBで1ページのPDF、5MBだが巨大なページ寸法を持つPDF）
- ページ数はページの複雑さや寸法を表さない（20MBで10,000ページのPDF、1MBだが展開後に大きくなる画像）
- 同じ入力でも操作によって負荷モデルが異なる（結合、分割、crop、linearize、PDF→画像、圧縮）
- ローカルアプリであり、共有サーバー資源を保護する必要性が低い
- 正常に進行している長時間処理とハングを、経過時間だけで区別できない

## 決定

Graphics Workbenchは、入力ファイルサイズおよびPDFページ数について、アプリケーション共通の固定上限を設けない。

変換、結合、分割、抽出、圧縮などの本処理について、アプリケーション共通の実行時間上限を設けない。正常に進行している長時間処理は自動終了せず、ユーザーによるキャンセルで停止する。

タイムアウトは、外部ツールの起動確認、通信、キャンセル後の終了猶予など、正常な完了時間を合理的に限定できる制御処理にのみ使用する。

ファイルサイズやページ数だけを理由とした確認ダイアログは表示しない。大きな入力の処理中は、取得可能な場合は現在の処理、処理済み数、総数を表示し、ユーザーがキャンセルできる状態を維持する。虚偽の進捗率は表示しない。経過時間タイマーを全操作に追加することは必須ではない。

## キャンセルの保証と処理方式

キャンセルの反映は処理方式によって異なる。

- Ghostscript、qpdf、pdftocairoなどの外部プロセス: キャンセル要求はプロセスツリーへ伝播し、終了猶予後に強制終了する。比較的強く保証できる。
- Extension Host内のmupdf / Sharp処理: `readFile`、`openPdfDocument`、`graftPage`、`saveToBuffer`などの同期区間ではキャンセルが即座に反映されない。キャンセル保証はbest effortであり、大きな入力ではイベントループが一時的に塞がり、キャンセルやメモリ不足（OOM）の処理が遅れる可能性がある。

「入力全体をメモリへ展開する必要が生じた場合」という再検討条件は将来の話ではなく、現在のmupdf系処理（並び替え、回転、分割、結合）がすでに該当する。そのため再検討条件として扱うのではなく、既知の制約として認識する。長期的には重いmupdf処理をWorker Threadまたは子プロセスへ隔離することを検討するが、このADRの採用判断（一律上限を設けないこと）は維持する。

この方針は「無限の入力を必ず処理できる」ことを保証しない。処理可能範囲は入力内容、対象操作、外部ツール、OS、利用可能なメモリ・ディスク、ユーザーのマシン性能で決まる。

## 理由

- 任意の固定値は軽い処理を不必要に拒否し、負荷の高い小さな入力を通す可能性がある
- ユーザー環境の性能差が大きく、共通値で安全側を保証できない
- ローカルアプリでは共有インフラ保護を目的とした一律上限が不要
- 長時間処理とハングを時間だけで区別できないため、一律タイムアウトは誤って正常処理を終了し得る
- 一律拒否より、安全な処理実装、キャンセル、cleanup、atomic commit、明確なエラー報告を優先する

## 結果・影響

利点:

- 処理可能な入力を一律値で拒否しない
- 任意の制限値を追加・調整する議論を繰り返さない

不利益:

- 非常に大きな入力では処理時間が長くなる
- メモリ不足やディスク不足が発生し得る
- 外部ツールが失敗する可能性がある
- ユーザー環境によって処理結果や所要時間が異なる
- すべての入力を処理できることは保証しない
- キャンセルとcleanupを正しく実装する責任が増える

リソース不足、壊れた入力、外部ツールの失敗、OSによるプロセス終了は、事前に一律拒否しない「想定される実行時エラー」として扱う。失敗時は以下を満たす。

- 元の入力ファイルを変更しない
- 不完全な出力を正式な出力先へcommitしない
- 一時ファイルとstagingを可能な範囲で削除する
- 子プロセスおよび必要な子孫プロセスを残さない
- 原因を識別できるエラーを表示する
- 失敗後に再実行可能な状態へ戻す

## 例外

操作固有の制限またはタイムアウトを追加できるのは、次のいずれかを必要条件とする。

1. 依存ツールまたはファイル形式仕様に明示された上限
2. 再現可能なクラッシュ、データ破損、応答不能
3. 実測可能なセキュリティ上の問題
4. 正常なら一定時間内に完了すると仕様上判断できる制御処理
5. 現在の実装では回避できない、操作固有の技術的制約

次の理由だけでは制限を追加できない。

- 大きいと遅そう
- メモリを使うかもしれない
- 念のため
- なんとなく安全そう
- 他のアプリにも制限がある
- 小さい入力しかテストしていない
- 実装が簡単になる
- ユーザーが間違えて選ぶかもしれない

セキュリティガード（decompression bomb対策のピクセル上限、SVG外部リソース読み込み防止、パストラバーサル防止、workspace外書き込み防止）はこの決定の対象外であり、単なるファイルサイズ制限と混同しない。

## 見直す条件

次のいずれかが発生した場合のみ、この決定を再検討する。

- 処理をクラウドまたは共有サーバーへ移行した
- 複数ユーザーが同じ計算資源を共有するようになった
- 実際の障害報告が継続的に発生した
- 外部ツールやファイル形式に明確な制約が追加された
- 具体的なセキュリティ問題が判明した
- OSやVS Code Extension Hostの制約により再現可能な重大障害が発生した

上記に該当しない限り、好みや不安だけを理由にこの決定を開き直さない。「入力全体をメモリへ展開する必要が生じた」は将来条件ではなく、現在のmupdf系処理がすでに該当する既知の制約として扱い、[キャンセルの保証と処理方式](#キャンセルの保証と処理方式)で管理する。
